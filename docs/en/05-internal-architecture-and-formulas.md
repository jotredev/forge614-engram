# 05 (EN). Architecture and Search

Forge614 Engram uses a feature-oriented modular monolith:

```text
src/modules/         pure domain types and rules
src/app/             use-case coordination
src/infrastructure/  SQLite, PostgreSQL, filesystem, Git, and release adapters
src/interfaces/      CLI, terminal prompts, and MCP stdio server
src/shared/          errors and shared utilities
```

Dependency rules are enforced by architecture tests. Interfaces call application public entries; they do not open SQLite or import infrastructure directly. Sibling products use Engram's public SDK or CLI, never private source folders.

SQLite is the durable source of truth. FTS5 performs literal lexical full-text search. Reinforcement changes result ordering using repeated observations and recency; it does not use embeddings and does not assert factual truth.

From schema 11 (memory intelligence, 1.7.0) a second FTS5 index over whole words (`unicode61`, accent-insensitive) sits next to the trigram index, together with side tables for memory metadata (short version, review date, replacement, affected projects), session activity and each group's source project. Those tables stay outside the memory version, so replication formats 1–3 do not change. A new database (whose file did not exist) is born at level 11 without a backup; on an existing database, even without a configuration, level 11 is enabled only with `intelligence-enable`, with a backup and verification; the MCP server never migrates the database.

The schema-11 hybrid search builds the query by dropping filler words (Spanish and English), folding accents and case, and joining the remaining terms with OR (16 at most); when every word is filler, all of them are used. In the word index, terms of 4 or more letters match by prefix; in the trigram index, terms of 3 or more letters match anywhere, both as written and with accents folded. Each index contributes up to 50 candidates; they are fused by reciprocal rank fusion (`1/(60+rank)` in each list where a result appears) and the result is multiplied by the same reinforcement multiplier `fts5` already uses (pinned, recency, stability): `orderScore = -(rrf × multiplier)`, lower is better. A result is dropped unless it contains at least 2 of the query terms (all of them when there are fewer than 2), matched by substring for terms of 3 or more letters and as a whole word otherwise; a query with no words at all (only punctuation) returns nothing. Saving a new memory without a topic also computes Jaccard similarity over distinct words (filler and accents removed) against the other active memories of the same scope and owner; a score of 0.25 or higher is reported as a look-alike (up to 3; see chapter 4).

With schema 11, starting or replaying a runtime session, saving a memory or a confirmation with a runtime session (explicit or inferred, never manual), a session summary, and closing the session all count as activity and record `session_activity.lastActivityAt`, clearing any leftover `interruptedAt` (chat messages do not count as activity). A session's effective activity is `coalesce(lastActivityAt, max(session_entries.recordedAt), startedAt)`. Since 1.7.1, opening a runtime session marks nobody, and classification is by elapsed time alone: any `interruptedAt` mark left by a database that ran 1.7.0 is ignored entirely (the column stays, for that reason). `previousInterrupted(projectId)` looks, among the project's open runtime sessions, for the most recently active one whose last activity is strictly earlier than now minus 30 minutes (`PARALLEL_MINUTES`), tie-broken by ascending `sessionId`, and reports `interruptedAt` as that last activity. `parallelSessions(projectId, sessionId)` looks for the project's other open runtime sessions whose last activity is at or after that same 30-minute boundary (inclusive: at exactly 30:00 a session still counts as parallel), most recent first and capped at 3. Session inference (`inferredSessions`) is unchanged: it still uses the 6-hour window (`INACTIVITY_HOURS`, used only for inference) and excludes sessions carrying a mark, instead of the 7-day window used below schema 11.

With schema 11, every `ecosystem` save (`save`, `saveWithSession`, CLI `save`, and MCP `memory_save`) and every move into a group check the board rules in this order: the type (`decision`, `procedure`, or `warning`; `ECOSYSTEM_TYPE_NOT_ALLOWED`); the effective `affects`, meaning the ones sent or, if none, the ones already stored, which must be at least 2 names (`ECOSYSTEM_AFFECTS_REQUIRED`) and each the exact name of a project that is a member of the group (`ECOSYSTEM_AFFECTS_UNKNOWN`); and finally the limit of 40 active memories (`ECOSYSTEM_BOARD_FULL`), which is only checked when a new memory is added to the board, not when an existing one gets a new version. The limit counts the group's active `ecosystem` memories, including those without a topic; it does not count the status note (`ecosystem/estado-actual`) or session summaries (`session/*/summary`), and group session summaries do not follow the other rules either. The status note checks the author first (`ECOSYSTEM_STATUS_FORBIDDEN`), then the type, which also admits `fact`, and then the 600 characters (`ECOSYSTEM_STATUS_TOO_LONG`); it does not ask for `affects` and is always pinned. The source project lives in the `ecosystem_sources` table (one row per group: `groupId`, `projectId`, `setAt`).

The startup block (format 2, `startupBlock`) is built with reads only, in one transaction. Essentials gathers the active pinned memories of the personal notebook (`shared`; a project memory on the same topic hides the shared one), of the group's board (the `ecosystem/estado-actual` status note first) and of the project, in that order, and within each newest first. The index gathers the titles of the active unpinned memories of the board and the project, alternating one from the board and one from the project so that neither drawer crowds out the other; it leaves out session summaries and the unpinned personal notebook. With schema 11, superseded memories are also left out, the short version replaces the title in essentials, the `[verify]` mark appears, and the session left open (more than 30 minutes without activity, `PARALLEL_MINUTES`) is included. The limits (5,000 in total, 1,500 for essentials, 800 for the previous session) are counted in Unicode characters; each list is filled in order and stops at the first line that does not fit, and what is left out is added up in `omitted`. The widest possible header is reserved before filling, and the final header prints the block's exact occupancy (`<chars>/5000 chars`).

Formats 1–3 PostgreSQL synchronization transfers a versioned snapshot of local state. It is optional, explicit, and cannot replace the local SQLite/FTS5 read/write path. Format promotion requires `sync --upgrade-format` after every participating device is compatible. A new database (schema 11) already uses format 3, so its first `sync` against a replica in an earlier format, including a freshly created one, stops with `SYNC_UPGRADE_REQUIRED` until `sync --upgrade-format` is used. `ecosystem` memories are not replicated through this path: without the cloud on, `sync` (with or without `--upgrade-format`) uses this path and stops with `SYNC_ECOSYSTEM_UNSUPPORTED` if they exist; `sync --upgrade-format` always uses this path, even with the cloud on. This path is now the deprecated mechanism (sunset 2027-03-31, acta 0024) now that the cloud mechanism exists.

## Cloud: the same memory on another Mac (schema 12, since 1.8.0)

Schema level 12 (turned on only by `cloud on`, never by default) adds a local pending-changes queue (`cloud_outbox`) fed by SQL triggers on every table that travels (projects, groups, memberships, group sources, each project's Git remote, memories with their version history and metadata, sessions, entries, summaries, and confirmations): every local save enters SQLite and the queue in the same transaction, so nothing is lost if the laptop closes before it uploads. A guard (`cloud_state.apply_guard`) turns those triggers off while a change downloaded from the cloud is being applied, so what just arrived is not re-queued. On Neon, `forge614_sync.changes` stores each change as a consecutively numbered row with its `payload` as a JSON object (`jsonb`) and its own `change_id`: if Neon's confirmation is lost after uploading a batch, retrying does not duplicate anything (`ON CONFLICT (change_id) DO NOTHING`). Each Mac remembers in `cloud_state.last_applied_id` the highest number already applied and asks only for later ones.

A background task inside the MCP server itself (it starts only once the database has gone through `cloud on`) uploads the queue in order and downloads what is new every 30 seconds, plus one extra cycle right after a save; a network error does not interrupt anything, it is retried on the next cycle. At session start (`startup-context`, `memory_context`) with the cloud on, it waits at most 1 second for what is new to arrive before continuing with local data (if Neon is asleep and does not wake up in time, what is new arrives on the next cycle). With the schema already created, `PostgresReplica` checks its shape with a single read-only query instead of a multi-step transaction, so that 1-second wait actually has time to download something; Neon runs PostgreSQL 18, whose catalogued `NOT NULL` constraints (unlike PostgreSQL 16) are excluded from that comparison without weakening validation.

When applying what was downloaded: a change from the installation's own device is never rewritten, it only advances `last_applied_id`; an unknown `kind` or a `payload` with other columns is skipped with a notice (`CLOUD_ROW_SKIPPED`) without stopping the rest of the batch; the existing secret filter (`findSecret`) also applies to what arrives, and text that looks like a secret is skipped with a notice (`SECRET_REJECTED`) without the value. For most tables the row with the most recent date wins; for a memory whose version number a local change already occupies, the incoming version is relocated to the next free number and both stay in history: the most recent one active, the other kept, with a notice shown once in the next `memory_session_start`. A project without `.forge614/project.json` on the other Mac is recognized by its normalized Git remote (`origin`), stored in a table that also travels; if two local projects share a remote, neither is bound — it is never guessed.

With the Neon connection string, the only parameter accepted besides `sslmode` is `channel_binding` (`require`, `prefer`, or `disable`): it is accepted and ignored, because Engram already requires verified TLS outside loopback.

The product currently ships verified macOS and Linux standalone binaries. There is no Windows native addon, installer, or release artifact in the current product.
